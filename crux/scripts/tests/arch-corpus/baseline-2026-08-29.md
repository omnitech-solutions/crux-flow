# Arch stack-pack baseline — 2026-08-29

What the **current** stack packs extract from **real** repositories. Every
number here was produced by running the deriver as it stands today; no
extractor, detector or grade function was changed to produce them.

Before this measurement the evidence that any language pack[^spine] extracts a
useful spine from real code was zero: the packs were validated by content assertions
against synthetic fixtures of 9-15 files, and the one pack with real-repository
coverage — the crux dogfood pack — is the one pack downstream users never get.

Reproduce:

```bash
uv run python3 crux/scripts/tests/arch-corpus/fetch.py           # ~78 MB, 10 clones
uv run python3 crux/scripts/tests/arch-corpus/derive_corpus.py   # 0.7 s, exit 0 = matches goldens
uv run pytest crux/scripts/tests/test_arch_corpus.py -q
```

## Method

Ten repositories, pinned by commit SHA in `corpus.yml`, shallow-cloned into the
gitignored `.cache/`. Each is derived with a scratch tree directory inside its
own clone, removed before and after every derive, so no corpus repository is
mutated and no derive sees a previous derive's output. Nothing under `bionic/`
is touched.

Two counts stand in for "entities extracted", because those are the two shapes
the spine renderers emit: `rows` counts markdown table data rows (an entity
column, a route, an ADR), and `edges` counts `-->` lines in the mermaid module
graph. `n_sources` is the deriver's own `inputs_found` count.

Two caveats about the numbers, both stated so they are not read as pack defects:

* **`decision-index` is stubbed for all ten repositories.** It reads an ADR
  tree, and none of these repositories has one. The stub is correct. Every
  summary below therefore reports the stub rate twice — with and without it.
* **The confidence grade is measured as the code computes it**, including for
  concerns whose grade the empty grading tables make unreachable.

## The confidence layer: prediction confirmed, with one correction

The proposal predicts that no corpus repository triggers a non-`high`
grade,[^grade] because `_CONFIDENCE_FLOORS` and `_PARTIAL_CAPTURE_PROBES` are
empty. Measured:

| grade | count | share |
|---|---|---|
| populated / `high` | 17 | 17 of 17 populated concerns |
| populated / `medium` | **0** | — |
| stubbed / `low` | 2 | djangoproject-com data-model + api-surface |
| stubbed / `none` | 21 | — |

**Confirmed for every populated concern: 17 of 17 grade `high`, and `medium` is
unreachable.** A concern with one captured source grades the same as one with
537. `fastapi-fullstack` data-model grades `high` while extracting zero
entities; `wagtail-bakerydemo` module-graph grades `high` on a graph with zero
edges.

**Corrected on one point: two grades are not `high`.** Both are `low`, both on
`djangoproject-com`, and both come from the expectation-marker path rather than
the floor path — `django` appears in `pyproject.toml`, which is one of the six
authored markers. Those two are also the only two escalation offers in the whole
corpus. The correction sharpens the proposal's case rather than weakening it:
the marker table covers 2 of 12 pack-concern pairs, so **every one of the 21
other stubs reports "no expectation marker present"** — including a Rails app
with 381 routes in `config/routes.rb` and a Phoenix app with 147.

## Detection: two mis-detections in ten

* **`wagtail-bakerydemo` — a Django application resolved to the node pack.**
  It has no `pyproject.toml` and no `setup.py`, so `_detect_python` is false; it
  has a `package.json` for its frontend assets, so `_detect_node` is true. The
  cost is measurable: `detect_package` finds the `bakerydemo` package and the
  Python data-model detector fires, so the python pack would have populated both
  module-graph and data-model. Instead the node pack produced a 4-node,
  zero-edge module graph over two static asset files and two lint configs.
* **`sequelize/express-example` — an Express application resolved to no pack.**
  The application lives in `express-main-example/`; the repository root carries
  no marker file at all, so detection falls through to the empty stub pack and
  all four concerns stub.

Detection is right on the other eight, including the two polyglot cases where
precedence decides: `fastapi-fullstack` (root `pyproject.toml` + root
`package.json` → python) and `papercups` (`mix.exs` → elixir, with a JS assets
tree present).

## Every stub says the same false thing

All 23 stubs render the identical line:

```
> _no extractor for this stack — empty-but-valid spine file._
```

For 20 of them a pack WAS selected and an extractor DOES exist — it declined,
or it ran and found nothing. For the remaining 3 the sentence is true of the
resolved pack and false of the repository, which is a supported Express app the
root-marker detector missed. **The count of stubs where "no extractor for this
stack" is the accurate explanation is 0.**

|---|---|---|

## Four findings the stub rate alone does not show

**1. The Elixir api-surface fails on every conventional Phoenix application,
for two independent reasons.**

`_elixir_router_files` collects `**/router.ex` plus any `.ex` file whose text
matches `Phoenix.Router`. Every `mix phx.new` application has
`lib/<app>_web.ex` — the entrypoint module whose `def router` quote block
contains `use Phoenix.Router`. That file sorts BEFORE `lib/<app>_web/router.ex`
in POSIX order, because `.` (0x2E) precedes `/` (0x2F). The single-primary rule
therefore picks the macro-definition file, which declares no routes, and the
extractor returns the stub. The real router is dropped as an unnamed residual:
the "additional routers not merged" line only renders on the populated path, so
the file that holds the routes is never even mentioned. Selected directly,
`live-beats`'s real router parses to 8 routes — so this defect alone costs that
repository its entire api-surface.

The second reason survives a fix to the first. `papercups`'s real router parses
to **0 routes even when selected directly**, because `_ELIXIR_VERB_RE` requires
the space-delimited spelling `get "/ping", PingController, :ping` and papercups
writes the parenthesized spelling `get("/ping", PingController, :ping)`. Both
are idiomatic; the formatter's `locals_without_parens` setting decides which a
project uses. 147 route declarations match no regex.

**2. `populated` does not mean "found something".** Two of the 17 populated
concerns carry zero entities of the concern's own kind:

* `fastapi-fullstack` data-model — 0 tables. The header says "Derived from
  SQLAlchemy declarative models and the Alembic migration timeline"; what
  rendered is 5 Alembic migration rows and no entity table, because the
  application's models are SQLModel classes, which the SQLAlchemy scanner does
  not recognize. It grades `high`.
* `wagtail-bakerydemo` module-graph — 4 modules, 0 edges, of which two are lint
  configuration files. It grades `high`.

**3. The Node route scan drops the mount prefix and misses chained routes.**
`express-boilerplate` declares 14 endpoints across `src/routes/v1/`; 9 were
extracted (64%). The 5 missed are the `router.route('/:userId').get().patch()
.delete()` chains in `user.route.js`. Separately, **all 9 extracted paths are
wrong**: the scan is per-file and never composes `app.use('/v1/auth', route)`,
so it reports `POST /login` where the application serves `POST /v1/auth/login`.
`nestjs-prisma-starter` extracted 2 of its 2 REST endpoints correctly; its real
API is GraphQL, which no probe covers.

**4. Ruby is the pack that works.** Zero stubs on six real concerns:
`rubygems.org` yields 56 tables (463 column rows) from `db/schema.rb`, 381
routes from `config/routes.rb`, and a 537-file, 619-edge module graph;
`codetriage` yields 122 column rows, 41 routes, and 96 edges. The routes
extractor is the regex one, and it names its own under-count residual
(`member`/`collection` blocks, `shallow:` nesting, route concerns).

## Goldens

`golden/<name>/` holds the four spine files plus `_meta/coverage.json` for each
repository: 50 files, 536 KB. They are **baseline** goldens — they record what
the packs produce today, stubs and all. Their job is to make the refactor
provable: splitting the monolith into `core.py` plus per-pack modules must leave
all 50 files byte-identical.

Re-derivation is byte-stable: a second derive over the same cache reproduces all
50 files exactly. The largest golden is `rubygems-org` at 150 KB; the smallest is
`sequelize-express-example` at 1.9 KB, which is four stubs.

Re-bless deliberately, and review the diff:

```bash
uv run python3 crux/scripts/tests/arch-corpus/derive_corpus.py --bless
```
