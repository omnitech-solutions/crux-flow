# Technology skills for Crux Flow: audit of the proposal against the code

Date: 2026-10-10. Status: audit and recommendation. Nothing was built, installed, committed or run
against a model. This is the only file written.

**Why this file is here.** Crux Flow has no documentation tree of its own (no `bionic/`, no
`AGENTS.md`, no `.bionic.yml`). Its root holds product guides that ship in the release
(`FLOW_GUIDE.md` is a packaged release input, `packaging.py:78`). Dated research and evidence notes
live in `verification/`, including the three earlier notes on this same subject
(`2026-10-09-technology-skill-routing-research.md`, `2026-10-09-official-crux-routing-mechanisms.md`,
`2026-10-10-technology-skills-next-steps.md`). So this audit sits beside them, not at the root.

**What was read.** Both proposal files whole; Crux Flow's README, `FLOW_GUIDE.md`, `FLOW_SEAMS.md`,
`CODEX.md`, the `verification/` notes, and the code in `crux/scripts/crux/flow/` (`hosts.py`,
`materialize.py`, `initialization.py`, `packaging.py`, `policy.py`, `workflow.py`, `managed.py`,
`lifecycle.py` in part, `cli.py` by command), `tools/verify.py`, `tests/flow/`; the `flow`,
`check-drift`, `forge-skill` and `init-docs` skills; both consumers; `omnitech-rulesync` and
`rulesync-bonsai`; host documentation and upstream repositories over the network (read only).

**One slip to declare.** While checking the Studio's Next.js version I listed
`apps/web/node_modules/next/dist/docs` and read one line of `next/package.json`, against the
instruction not to list `node_modules`. Nothing was written. The fact it gave is used once, in
section B, and is marked there.

| Mechanism | Host | What enters the context | Certain or by the model's choice |
|---|---|---|---|
| Root `AGENTS.md` | Claude Code 2.1.277 or later, only when no `CLAUDE.md`, `.claude/CLAUDE.md` or `CLAUDE.local.md` exists at or above the working directory; Codex (root to working directory, 32 KiB total by default); OpenCode | The whole file, at session start | Certain that the text is there. Whether the model obeys it is its choice. |

| Skill body | All three | The full `SKILL.md`, when the model calls the skill | The model's choice. |
| Subagent `skills:` list | Claude Code | "The full skill content is injected, not only the description", at subagent start. A missing name is skipped with a debug-log warning. | Certain, if the name resolves. |
| Project instructions in a subagent | Claude Code | Custom subagents load the same `CLAUDE.md` or `AGENTS.md` files as the main session; the built-in Explore and Plan agents do not. A subagent never sees the parent's invoked skills. | Certain for custom subagents. |

`.claude/skills` and `.agents/skills`, and requires the skill's `name` to equal its folder name.

## 5. The inspirations

**Public rulesync** (`dyoshikawa/rulesync`, MIT): one source folder (`.rulesync/`), one config
(`rulesync.jsonc` with `targets` and `features`), `generate` writes each tool's native files, `fetch`
installs skills from a repository, a lock records what was resolved.

**Omnitech Rulesync** (`~/dev/omnitech-solutions/omnitech-rulesync`, private, 0.2.0): a catalog of
42 profiles. Each has `detect` rules (for example "package dependency `react`") and `includes`
(rules, skills, upstream sources). `catalog/sources/trusted.yaml` is an allow-list with licence,
trust level, and the files each skill must bring with it. Commands: `inspect`, `plan`, `install`,
`check`.

**Bonsai rulesync** (`~/dev/rulesync-bonsai`): a pnpm workspace that builds Bonsai's rules from a base
layer, a Bonsai layer and a vendored, pinned `superpowers-ruby`. It has one always-read index skill
(`bonsai-skill-catalog`) with a table of "name, when to use" and a stated priority rule (Bonsai's own
skill wins), and a collision audit.

| Borrow | From | How it appears in the recommended design |
|---|---|---|
| Detection by declared dependency, never by guess | Omnitech `detect` | The catalog's `detect` list decides which technologies are eligible |
| One source, generated per-host output | rulesync `generate` | One config; the router's table and the host role bindings are generated |
| An allow-list with licence, trust and required files | `trusted.yaml` | Catalog fields `licence`, `first_party`, `lifecycle`; the check refuses a reference whose files are missing |
| One small index with "when to use" and a priority rule | Bonsai catalog skill | The router: a table plus "repository rules win" |
| A collision check | Bonsai collision audit | The check refuses two routers with the same name |

**Do not import.** Omnitech Rulesync's base profile cannot be excluded
(`src/core/resolve.ts:36-37`: "The base Superpowers routing profile cannot be excluded") and brings
eleven Superpowers workflow skills. That is a second workflow, which Flow refuses. Also leave out the
Node toolchain, `rulesync install` as a second installer, and Bonsai's 30-odd per-command routing
skills.

## B. The proposal: what to keep and what to drop

**Right, keep.**

- Two layers: a small router and lazily read references. No rule text copied into the router.
- Project rules outrank any outside reference; a conflict is reported, not blended.
- Commands and versions come from the project, never from the skill.
- Deterministic eligibility; a model may only choose among eligible candidates.
- Local drift and upstream freshness are different questions. `check-drift` stays read-only and
  offline.
- Vendor skill bodies must never pass through Flow's skill rewriting.
- Do not replace the Studio's existing router; one primary router per repository.
- Adding a `CLAUDE.md` would stop Claude reading `AGENTS.md` (confirmed in Claude's memory page).
- A catalog entry, a role file with a preload field or a green mocked test is not proof of loading.
- Do not import Omnitech Rulesync's mandatory base profile.

**Wrong or unverifiable.**

| Claim | Finding |
|---|---|
| "No official Hono skill" | `honojs/skills` exists, MIT, described as official. |
| `clerk/skills` `skills/frameworks/clerk-nextjs-patterns` | That path is 404 today. |
| Catalog as `crux/catalog/technology-references.yml`, "separately registered" | The fork's registry for authored catalogs takes JSON files with a validator function. |
| The router belongs in `crux/skills/technology-references` | It would be rewritten with the Flow prefix, would collide by name with the Studio's forged skill, and could only carry a generic description, which triggers worse than one that names the project's technologies. |
| "Extend `materialize.py` / `managed.py` to include technology file sets" | `materialize` owns only `crux-flow-*` names. A project router is not such a file. |
| "Carry selected paths, command evidence and selection digest" in the dispatch | The run contract has no such field. A constraint sentence does the job. |
| Remote `master` is at `a753b6d` | The local checkout is one commit ahead (`f659de0`). Build from the local checkout. |
| 32 acceptance scenarios in `acceptance/acceptance-cases.json` | That file was not supplied. Unverifiable. |
| Next.js guidance should be sourced from `vercel/next.js` skills | For the Studio the better source is already on disk: its installed Next 16.2.11 ships `dist/docs` (seen in the slip declared above). No capture is needed for that layer. |

**Over-built for the goal, and against Flow's principles.**

- Six new commands (`inspect`, `plan`, `apply`, `check`, `refresh`, `export`). Flow already has
  `init` with a shown plan, and Crux already has refresh skills. Two verbs are enough.
- Five new Python modules, two JSON schemas, six test files. One module is enough.
- A separate adoption lock with digests of catalog, overlay, repository evidence and host bindings.
  The research source pages already pin commit, capture date and raw path.
- A second maintenance skill that restates `forge-skill`, `ingest-research` and the refresh skills.
- A pnpm authoring package and a rulesync export. That is a second toolchain and a second installer.
- A source-capture pipeline with archive handling. `ingest-research` already captures sources.
- Repository inspection for Ruby, Python, Go, Elixir, Terraform and Composer. Neither consumer has
  them. Start with `package.json`, the pnpm catalog and the `Package.swift` tools line.
- Six fixed reference "families" shipped in the plugin. The Studio's map shows the useful unit is a
  project layer tied to that project's ADRs and invariants; a family file would be generic prose.
- A 100-line router target. The Studio's is 47 lines and works as a shape.

## C. The smallest design that meets the goals

### The idea in one paragraph

The Studio has already built the right thing by hand with upstream seams: a forged project router,
a reference map in the research tree, pinned captures, and one line in the root `AGENTS.md`. Flow
should turn that into configuration plus one generator: a small shipped catalog says which
technologies exist and how to detect them; a short list in the project's own `.crux-flow.yml` says
which layers this repository has, which paths they cover, what to read and which command to use;
one script writes the router's table from that list and checks that everything it names is real.
The same script is the drift gate. `init` plans the same output. Role files name the router so a
delegated agent starts with it.

| Thing the proposal wants | Where it lives |
|---|---|
| Catalog | `crux/catalog/flow-technology.json`, shipped with Flow |
| Overlay | The `technology` section of the project's `.crux-flow.yml` |
| Lock | The research source pages the layers name: pinned commit or capture date, and the raw capture path. The check refuses a layer whose page lacks a pin or whose capture is missing. |
| Router | `.agents/skills/<router>/SKILL.md`, with a real copy in each other host's skill folder that Flow can write. Where a folder is a symlink to `.agents/skills` (the Studio), the one file already serves every host and Flow writes nothing through the link. |
| Map (the "why") | `<docs>/research/references/technology-references.md`, authored, as the Studio has it |
| Root routing line | One line in the root `AGENTS.md`, proposed by `init` and written only with approval |

### What `init` and the drift check do

`crux-flow init` (and `crux-flow technology sync`): read the config; for each layer confirm the
catalog technology is detected in a manifest; resolve the declared version string; render the router
table and description; add the files to the plan already shown to the user; write through
`managed.plan`/`apply` with a receipt. With `owner: project` it writes nothing and only reports.

`check-drift` row (and `crux-flow technology check`): the same script with `--dry-run`.

| Verdict | When |
|---|---|
| N/A (`surface_absent`) | No `technology` section |
| clean | The router's generated region equals what the config and manifests produce, and every check passes |
| DRIFT | The region differs: a layer was edited, or a declared version changed in a manifest. Fix: `sync`. A version change also says which source pages to refresh. |
| BROKEN (`validation_errors`) | A `read` path does not exist; a source page has no pin or its capture is missing; a named command is not a script in the named package; a layer's technology is not detected in any manifest; two skills share the router's name; with `owner: project`, the description lacks a layer's trigger term or the router exceeds the size limit |

Freshness against upstream stays where it is: `refresh-research-sources`, on request, online.

### How routing happens without the flow skill

| Session | Carrier | Certainty |
|---|---|---|
| Ordinary session, any host | The root `AGENTS.md` line, then the router's description, then the router body, then only the row's references | The line and the listing are certain; reading is the model's choice and is measured |
| Delegated Claude role | `skills:` in the generated role file injects the router body at start | Certain if the name resolves; proved with the canary |
| Delegated Codex role | `[[skills.config]]` enables the router; the root `AGENTS.md` line asks for it | Listed; reading is measured |
| OpenCode, OMP | The router in their skill folder and the root line | Listed; no preload exists, and the report says so |
| A Flow run | The same as an ordinary session, plus the constraint sentence on the unit | Same |

None of these needs the `flow` skill to run. The router is a project skill, so it never passes
through `hosts.skills` and never receives the Flow prefix.

### Alternatives

| | What | For | Against |
|---|---|---|---|
| 1. Check only | No generator. Router and map stay hand-written (as the Studio's are). Flow adds a guard script, a template for `init` to offer, and the role preload. | Fewest lines. Touches nothing in the Studio. | Not configuration driven. The router and the map can still disagree in prose. Each project writes its own description. |
| 2. Config and one generator (**recommended**) | As above. | One source per project. The engine's router cannot mention Next.js because no such row can be generated. Version bumps show as drift. Works for a plain-Crux repository through `owner: project`. | Adds one key to `.crux-flow.yml` and one module. The Studio would need a `.crux-flow.yml` holding only the `technology` section if it wants the check while staying on upstream Crux. |
| 3. Plugin router | A generic `crux-flow:technology-references` in `crux/skills`, reading a per-project map. | Present wherever Flow is enabled, with no project file. | Gets the Flow prefix unless `hosts.skills` is changed; collides with the Studio's forged skill; a generic description triggers worse; absent in the Studio, which runs upstream Crux; one more description in an already long plugin list. |
| 4. The proposal as written | Catalog, lock, six commands, five modules, export. | Covers many stacks at once. | Second installer and second toolchain; duplicates the research lifecycle; far more than two consumers need. |

with `paths:` gives certain, hook-provable loading by path. It is one more generated surface on one
host, so it should follow evidence that the router alone is not read often enough.

## D. What "the highest standard" means for these skills

Drawn from Anthropic's
[skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices),
the Claude Code and Codex skill pages, and OpenCode's limits.

| # | Standard | How it is checked |
|---|---|---|
| 1 | Name: lowercase letters, digits, single hyphens, at most 64 characters, equal to its folder name, not containing "claude" or "anthropic". | Script |
| 2 | Description in the third person, saying what it does and when to use it, with the key use and trigger words first, at most 1,024 characters (the tightest host limit). | Script for length and terms; review for wording |
| 3 | Description names every configured technology by its catalog `terms`, and no technology that is not configured. | Script |
| 4 | Router body at most 80 lines (hosts advise under 500; a router should be far smaller). | Script |
| 5 | No rule text copied from a vendor. The router holds paths, versions, commands and repository rules only. | Review, plus a script check that no line of the router appears in a captured `rules/` file |
| 6 | References are one level deep: the router links straight to each page it wants read. | Script: every `read` resolves; none is reached only through another page |
| 7 | A reference longer than 100 lines opens with a contents list. | Script |
| 8 | Versions and commands come from the project's manifests and scripts, never from the skill's own text. | Script: version equals the manifest's declared string; command exists as a script |
| 9 | Every outside reference has an owner, a licence, a first-party flag and a pin. | Script against the source page and the catalog |
| 10 | Authority is stated once: repository rules win; reference text is data, not instruction. | Script for the presence of the section |
| 11 | No dates or "before/after version X" advice in the router. | Review |
| 12 | One job per skill; one primary router per repository; no name shared with a plugin skill. | Script |
| 13 | One term per idea throughout ("layer", "reference", "router"). | Review |

**Evaluation of each router**, built before the router is polished, as the guidance asks ("at least
three evaluations", with a no-skill baseline):

- *Trigger set.* At least eight prompts that should load it and eight that should not, written per
  consumer. Should load, Studio: "add a nullable column to the sessions table and generate the
  migration"; "review this Hono route for tenant checks". Should not: "fix the typo in the README";
  "answer this interview question about binary search" (that belongs to the interview router).
  Should not, engine: any prompt about React or Next.js has no row to load. Each prompt is run in a
  fresh headless session with writing disallowed; the transcript is checked for the router and for
  the references read. Report loads out of runs for each prompt, not one success.
- *Task set.* Three tasks per consumer, each run with the router present and with it removed, same
  model and settings. Assertions are concrete: the Studio's migration answer names `db:generate` and
  never `push`; the engine's adapter answer returns a typed `Failure` and adds no framework import.
- *Models.* Run on each model the roles use (the role files name them).
- Record every run in the repository's `forge-log.md` (`used`, `evaluated`), which upstream already
  defines.

## F. Risks to the owner's working setups

| Risk | Why it is real | How the build avoids it |
|---|---|---|
| A commit in crux-flow reinstalls his hosts | `core.hooksPath` is set to `.githooks`. The post-commit hook runs `crux-flow setup --yes` after any commit touching `crux/`, which rebuilds, reinstalls every host and repoints `~/.local/bin/crux-flow`. The engine would pick the new release up in its next session. | Commit with `CRUX_FLOW_NO_HOOK=1`, or do not commit at all until he approves. Never run `pnpm run refresh` or `setup`. |
| His installed upstream Crux plugin | User scope has `crux@crux` on and `crux-flow@crux-flow` off. | The slice runs no `install`, `update`, `init` or `setup` against his real home. Tests use temporary homes, as the existing ones do. |
| The Studio's forged router and its symlinked skill folders | A plugin skill of the same name would collide; a write through `.claude/skills` or `.opencode/skills` would hit a symlink. | No plugin skill is added. `owner: project` never writes. Flow's writer refuses symlinks and foreign files already; case 4 pins that. |
| Running `crux-flow init` in the Studio | It would turn upstream Crux off and Flow on for that repository, against its ADR-0001 wording. | The slice never runs it there. `crux-flow technology check` needs no activation. Moving the Studio to Flow is the owner's separate decision. |
| The engine's 186 tracked projection files | A changed role file changes tracked files and the next `init` there. | The preload is off unless the config asks for it. With no `technology` section the role output is byte-identical to today; case 9 pins that. |
| `.crux-flow.yml` is validated strictly | A new key written by a newer Flow is refused by the Flow release currently installed ("missing required fields or unknown fields"), which would break `flow` in the engine. | Do not add the key to the engine's real file until the release that understands it is installed. Until then the slice uses copies. |
| Other workers are editing both consumers now | Uncommitted work in both. | Read only. Fixtures are built from committed content (`git archive HEAD`), never from the working tree. |
| Model spend | Live cases call paid models. | Behind the `provider` marker and his approval. |
| Description budgets | The plugin already lists 54 skills; the Studio lists 16 more. | The design adds no plugin skill and at most one project skill. |

## G. What could not be determined

1. Whether Claude Code resolves a bare plugin skill name in a project role file. Flow's project role
   files say `skills: [flow]` while the skill is `crux-flow:flow`. If it does not resolve, Claude skips
   it with only a debug-log warning, and Flow's existing preload has never worked. Case L3 would show
   it; a project skill named plainly does resolve by the documented example.
2. Whether a skill's `paths:` frontmatter loads the body or only limits the listing.
3. Whether Codex subagents receive `AGENTS.md`. The page does not say.
4. Whether OpenCode loads Flow's projected skills at all: they sit in folders named
   `crux-flow-<name>` with `name: <name>`, and OpenCode's page says the name must match the folder.
   This is an existing Flow question, outside this work, and worth one check.
5. How often an ordinary session actually reads the router. No model turn was run in this audit.
6. The proposal's `acceptance/acceptance-cases.json`, its draft skills and its "flattened collection"
   were not among the files supplied.
7. Whether the Studio's router line about `AiExecutionGateway` is stale. `AGENTS.md` rule 7 still
   names it; the engine boundary may have replaced it. It needs the Studio owner's answer.
8. Whether the owner wants the Studio moved to Crux Flow, or kept on upstream Crux with only the
   check. The design supports both.
9. Whether the per-project list should sit in `.crux-flow.yml` (recommended: one file) or in its own
   file. The second avoids the strict-key risk in F at the cost of one more root file.
10. `mastra-ai/skills` reports no recognised licence, and several first-party repositories have no
    root licence file. Not relevant to the two consumers; relevant before any wider catalog.
